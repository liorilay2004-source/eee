## 4. שלב א' — מיגרציות למסד (חובה לפני ההעלאה)

**למה קודם:** הקוד משתמש בטבלאות ובאינדקס `idx_prices_recent` שנוצרים במיגרציות. במסד לא ממוגר, `/api/health` ו-`/api/search` נכשלים.

**סדר וחוקים:** `0001_init.sql` ← `0002_seed_airports.sql` ← `0003_cache_extras_and_recent_index.sql` ← `0004_source_quota.sql` ← `0005_m8_deal_reports.sql` (אם מוזג) ← `0006_m11_price_alerts.sql`.
- 0001, 0002 ו-0004 בטוחים להרצה חוזרת (`IF NOT EXISTS` / `INSERT OR REPLACE`).
- **0003 מכיל `ALTER TABLE … ADD COLUMN` ולכן חייב לרוץ פעם אחת בלבד** (הרצה שנייה נכשלת עם "duplicate column name").
- 0004 יוצר את `source_quota`, מונה הבקשות של המקורות החיים האופציונליים (סעיף 6א). אין לו שום השפעה על החיפוש הרגיל, אבל **בלעדיו אף מקור חי לא יופעל**.
- 0006 מוסיף עמודות לטבלאות `watches` ו-`alerts` בשביל התראות המחיר (סעיף 6ב), ושורת משתמש אנונימית אחת (`anonymous-watches@watches.invalid`, כתובת שלא יכולה להתקיים). **גם הוא מכיל `ALTER TABLE … ADD COLUMN` ולכן רץ פעם אחת בלבד.** בלעדיו `POST /api/watches` עונה 503, והחיפוש לא מושפע.

**דרך 1 (מומלצת) — `wrangler` במסוף:**

```bash
git clone https://github.com/liorilay2004-source/eee
cd eee/worker
npm ci
npx wrangler login          # נפתח דפדפן לאישור (במחשב אישי)
npx wrangler d1 migrations apply eee-db --remote
```

ב-Codespaces או בכל סביבה מרוחקת `wrangler login` לא עובד (ה-callback מקומי). שם יוצרים טוקן API בהרשאות "Edit Cloudflare Workers" ו-"Account → D1 → Edit" ומגדירים אותו רק כמשתנה סביבה בטרמינל (`export CLOUDFLARE_API_TOKEN=…`, ללא כתיבה לקובץ), ואת ה-Account ID כ-`CLOUDFLARE_ACCOUNT_ID`.

`wrangler` מתעד ב-D1 אילו מיגרציות הורצו (טבלת `d1_migrations`), ולכן הרצה חוזרת בטוחה: הוא מריץ רק את החסרות (וגם אם כבר הרצת את 0001–0003, הפקודה תוסיף רק את 0004). פלט תקין (כך נראה מקומית, על מסד D1 מקומי זמני; אין כאן שום מסד אמיתי):

```
│ 0001_init.sql                          │ ✅     │
│ 0002_seed_airports.sql                 │ ✅     │
│ 0003_cache_extras_and_recent_index.sql │ ✅     │
│ 0004_source_quota.sql                  │ ✅     │
```

**דרך 2 — קונסולת D1 בדשבורד (בלי מסוף):** Storage & databases ← D1 ← `eee-db` ← Console; מדביקים כל קובץ לפי הסדר (0004 קצר, שורות ספורות). הקובץ 0002 גדול (כ-127 KB), וייתכן שיידרש לפצל אותו. **אזהרה:** `wrangler` לא יידע שהמיגרציות הורצו, ומאוחר יותר `wrangler d1 migrations apply` ינסה להריץ שוב את 0003 ויכשל. לכן בדרך הזו לא מריצים אותו על 0001–0004.

**דרך 3 — אני מריץ דרך המחבר ל-Cloudflare:** רק אם תיתן אישור מפורש (כי ביקשת לטפל ב-Cloudflare בעצמך). כ-10 שאילתות, ואני גם רושם אותן ב-`d1_migrations` כדי ש-`wrangler` יישאר עקבי.

**אימות אחרי המיגרציה** (בקונסולת D1 או `npx wrangler d1 execute eee-db --remote --command "…"`):

## 5. שלב ב' — העלאה

### דרך א' — Workers Builds (מהדשבורד, בלי מסוף; מומלץ אם אין מחשב)
1. https://dash.cloudflare.com ← **Workers & Pages** ← **Create application** ← **Get started** ליד **Import a repository**.
2. בוחרים חשבון Git (GitHub). אם מתבקש, מתקינים את אפליקציית Cloudflare על הריפו `eee`.
3. בוחרים את `eee` ומגדירים:

| שדה | ערך |
|---|---|
| Worker name | `eee-api` (**זהה ל-`name` ב-`wrangler.toml`**) |
| Git branch (production) | `main` |
| Root directory | `worker` |
| Build command | ריק |
| Deploy command | `npx wrangler deploy` (ברירת המחדל) |
| API token | ברירת המחדל (Cloudflare יוצר טוקן לבנייה) |

4. **Save and Deploy.** מהרגע הזה כל דחיפה ל-`main` מעלה גרסה חדשה אוטומטית.
5. ב-Settings ← Builds לבדוק שבנייה לענפים שאינם ייצור **כבויה**. כשהיא דולקת, כל ענף ו-PR מקבלים בנייה נפרדת (`wrangler versions upload` / preview), וזה לא מה שרצוי כאן.

שים לב: Workers Builds **לא מריץ מיגרציות**. את שלב א' עושים בנפרד, לפני ההעלאה הראשונה.

### דרך ב' — `wrangler` במסוף

```bash
cd eee/worker
npm ci
npx wrangler deploy
```

בסוף מודפסת הכתובת `https://eee-api.<…>.workers.dev`.

### אחרי כל העלאה — בדיקת עשן
אחרי כל `npx wrangler deploy` (או בנייה ב-Workers Builds) מריצים מהמחשב, מתיקיית השורש של הריפו:

```bash
bash scripts/smoke.sh                                   # ברירת מחדל: https://eee-api.liorilay2004.workers.dev
bash scripts/smoke.sh https://eee-api.<שלך>.workers.dev   # כתובת אחרת
```

הסקריפט צריך רק `bash`, `curl` ו-`python3`. הוא לא משנה כלום: קריאות GET ל-`/api/health`, `/api/deals`, `/api/calendar` (תל אביב–אתונה, החודש הבא) ו-`/api/explore` (מתל אביב, החודש הבא), וחיפוש אחד בלבד ב-`POST /api/search` (רחוק ממגבלת הקצב). בסוף מודפסת טבלת PASS/FAIL, וקוד היציאה הוא 0 רק כשהכול עבר. שורת הבריאות מראה את הקומיט שהועלה (`build`) ואת המיגרציה האחרונה שהוחלה על D1. אם מופיע `migrations pending` — הקוד חדש יותר מהמסד: מריצים את המיגרציות (שלב א') ובודקים שוב.

המזהה של הקומיט נכתב אוטומטית בזמן ההעלאה (`[build]` ב-`wrangler.toml` מריץ את `worker/scripts/gen-build-info.mjs`); אין צורך בשום צעד נוסף. בלי git הוא יופיע כ-`unknown`, ואם העלית מהמחשב עם שינויים שלא נשמרו בקומיט בתיקיית `worker/` יתווסף לו `-dirty`. אפשר להריץ את ההעלאה מתוך `worker/` (הדרך הרגילה) או מהשורש עם `--config worker/wrangler.toml`.

### דרך ג' — GitHub Actions
לא נוצר workflow להעלאה: מערכת ההרשאות חסמה אותו כ"Production Deploy", וביקשת לטפל ב-Cloudflare בעצמך. אם תרצה אותו, תגיד. הוא ידרוש שני סודות ב-GitHub: `CLOUDFLARE_API_TOKEN` (התבנית "Edit Cloudflare Workers" בתוספת "Account → D1 → Edit") ו-`CLOUDFLARE_ACCOUNT_ID`.

## 6. שלב ג' — סודות ומשתנים

בדשבורד: Workers & Pages ← `eee-api` ← **Settings** ← **Variables and Secrets** ← **Add**. **בוחרים בסוג "Secret"**, לא "Text".

או במסוף (הערך נשאל אינטראקטיבית ולא נשמר בהיסטוריית הפקודות):

```bash
cd eee/worker
npx wrangler secret put TRAVELPAYOUTS_TOKEN
npx wrangler secret put TRAVELPAYOUTS_MARKER
npx wrangler secret put RATE_LIMIT_SALT      # מחרוזת אקראית של 32 תווים ומעלה. למשל: openssl rand -hex 32
```

**נעילת האתר לשימוש אישי:** סוד אופציונלי אחד, `ACCESS_KEY` (`npx wrangler secret put ACCESS_KEY`). בלעדיו האתר פתוח לכולם. ההסבר המלא, כולל יצירת המפתח: סעיף 6ג.

**ארבעה סודות נוספים הם אופציונליים לגמרי** (מקורות מחיר חיים): `IGNAV_API_KEY`, `WEGO_API_TOKEN`, `SEARCHAPI_KEY`, `SERPAPI_KEY`. אפשר לא להגדיר אף אחד מהם, וזה המצב ההתחלתי המומלץ. לפני שמגדירים אותם קוראים את סעיף 6א:

```bash
npx wrangler secret put IGNAV_API_KEY        # רק אחרי סעיף 6א, ורק מחשבון חינמי
npx wrangler secret put WEGO_API_TOKEN
npx wrangler secret put SEARCHAPI_KEY
npx wrangler secret put SERPAPI_KEY
```

- סודות (Secret) לא נמחקים בהעלאה חדשה.
- **משתנים רגילים (Text) שהוגדרו רק בדשבורד עלולים להימחק בהעלאה הבאה**, כי `wrangler.toml` הוא מקור האמת שלהם. לכן `ALLOWED_ORIGIN` יוגדר בקובץ `wrangler.toml` (ב-`[vars]`) כשיהיה ממשק, ולא בדשבורד.

## 6א. מקורות מחיר חיים (אופציונלי, חינם בלבד)

**מה זה נותן:** Travelpayouts מחזיר מחירים שמורים (Aviasales, בני יומיים עד שבוע). עד ארבעה מקורות נוספים יכולים לתת **מחיר חי** לזוגות תאריכים מסוימים: אחרי הסריקה בוחרים את עד 4 זוגות התאריכים הזולים ביותר, שואלים כל מקור מוגדר על בדיוק אלה, ומחירם משולב בדירוג. כך מאשרים שמחיר שמור עדיין עומד, ולא תלויים בספק אחד. כל מקור מופיע ב-`meta.sources` בתשובה עם סטטוס משלו.

**הכללים, בקצרה ובבירור:**

1. **ארבעת הסודות (`IGNAV_API_KEY`, `WEGO_API_TOKEN`, `SEARCHAPI_KEY`, `SERPAPI_KEY`) אופציונליים.** מקור בלי סוד לא בשימוש, לא נספר, לא עולה כלום ולא מופיע בתשובה.
2. **פותחים כל חשבון אצל הספק במסלול החינמי שלו, ואף פעם לא מוסיפים כרטיס אשראי** (וגם לא אמצעי תשלום אחר, וגם לא מפעילים שם חידוש או שדרוג אוטומטי). בלי כרטיס בחשבון אין ממה לחייב, גם אם קרתה תקלה.
3. **הקוד עוצר לפני המכסה החינמית.** לכל מקור יש תקרת בקשות קשיחה **נמוכה** מהמכסה החינמית של הספק (מרווח של לפחות 10%, ובפועל גדול יותר), והיא נספרת ב-D1: המונה עולה **לפני** כל קריאה (כך שגם קריאה שנכשלה או נקטעה נספרת), קריאה נדחית כשהמונה הגיע לתקרה, ואם אי אפשר לקרוא או לכתוב את המונה (טבלה חסרה, שגיאת מסד) המקור נחשב כמי שנגמרה מכסתו **ולא נקרא**. אין ניסיון חוזר לקריאה שנכשלה. המונים לא נמחקים בניקוי היומי, והם נספרים רק כלפי מעלה. **מעל התקרה יש גם מנת יום:** כל מקור מקבל ביום UTC לכל היותר את התקרה שלו חלקי 30 (מכסה חד-פעמית) או חלקי 31 (חודשית), מעוגל למעלה (Ignav 27, SearchApi 2, Wego 1, SerpApi 4, Duffel 1), והיא נלקחת לפני יחידת המונה האמיתי, באותו כלל של כשל סגור (מנה שנגמרה או שאי אפשר לקרוא אותה = אין קריאה). בלי המנה, כמה לקוחות שמשנים פרמטר בכל חיפוש כדי לעקוף את המטמון היו מנצלים מכסה חד-פעמית שלמה בדקות, והיא לא מתחדשת אף פעם. המנות נשמרות בטבלה `rate_limits` (מפתח `quota:<מקור>`), ולכן אין להן מיגרציה, והניקוי היומי מוחק אותן אחרי יום.
4. **התקרות דורשות את מיגרציה 0004** (סעיף 4, מריצים אותה כמו האחרות). **כל עוד היא לא הורצה, אף מקור חי לא נקרא**, גם אם הסוד מוגדר.
5. **המתאמים נכתבו מתיעוד ציבורי ועדיין לא נבדקו מול השירותים החיים.** שדות שהתיעוד לא מבהיר נקראים בזהירות ונשארים ריקים, אבל ייתכן שהתשובה האמיתית שונה. ההפעלה הראשונה של כל מקור היא בדיקה: מפעילים אחד בכל פעם ובודקים (ראו למטה).

לכל מקור מספר תקרה אחד בלבד, בקוד, ואי אפשר לשנות אותו מסוד או ממשתנה. הקוד גם בודק בעצמו שהתקרה נמוכה מהמכסה (עד 90% למכסה חד-פעמית, עד 45% למכסה חודשית); תקרה שחורגת מזה גורמת למקור להיות מושבת. גבולות נוספים לכל חיפוש: עד 4 זוגות תאריכים, עד 12 בקשות יוצאות בסך הכול (יחד עם 30 של Travelpayouts ו-1–2 של שערי החליפין נשארים מתחת ל-50 של המסלול החינמי), רק אחרי סריקה טרייה שהצליחה במלואה. חיפוש שנענה מהמטמון אינו קורא לאף מקור חי ולכן אינו מוריד מהמכסות. המשימה המתוזמנת (ניקוי יומי) לא משתמשת בהם בכלל.

**הפעלה בטוחה, אחד בכל פעם:**

1. מריצים את מיגרציה 0004 (סעיף 4) ובודקים שהטבלה קיימת: `npx wrangler d1 execute eee-db --remote --command "SELECT source, period, used FROM source_quota"` (קריאה בלבד, בהתחלה ריק).
2. פותחים חשבון אצל ספק אחד **במסלול החינמי, בלי כרטיס**, ומגדירים את הסוד שלו (סעיף 6).
3. מריצים חיפוש אמיתי ומוודאים: `meta.sources` כולל את המקור עם `calls` גדול מ-0, `used` בפקודת ה-`SELECT` שלמעלה עלה, ובלוח הבקרה של הספק המונה שלו עלה בהתאם ואתה עדיין במסלול החינמי.
4. **בדיקת מחיר, לפני שמשאירים את המקור פעיל.** לוקחים מתשובת החיפוש כרטיס אחד ש-`source` שלו הוא הספק הזה, ופותחים ב-Google Flights (או באתר הספק) את אותו מסלול, באותם תאריכים, לנוסע בוגר אחד במחלקת תיירים. משווים את המחיר והמטבע שבכרטיס למחיר **הכולל של הלוך-חזור** לנוסע אחד. אם הם שונים ביותר מכמה אחוזים, או שהספק מציג רק את כיוון ההלוך או מחיר לקבוצה, מסירים את הסוד (`npx wrangler secret delete <NAME>`) ומדווחים לי. **עד שהבדיקה נעשתה, המחיר של המקור הוא הנחה ולא עובדה:** מחיר חי מחליף את המחיר השמור של אותה טיסה גם כשהשמור זול יותר, ולכן מחיר שגוי היה מנצח בכרטיס ואחר כך היה מוצג כ"הזול ביותר שנראה" בחיפושים הבאים. בפרט, ש-`price` של SerpApi הוא סך הלוך-חזור הוא הסקה מהדרכה של הספק ולא הבטחה מתועדת (`serpapi.ts`), וגם אצל Ignav התיעוד אינו אומר זאת במפורש (`ignav.ts`).
   הקוד מוסיף רשת ביטחון גסה בלבד: מחיר חי הנמוך מ-55% מהמחיר השמור הזול ביותר של אותו זוג תאריכים לא מדורג ולא נשמר (ואם כל מה שמקור החזיר נפסל כך, `meta.sources` אומר "quote(s) ignored: far below the cached fare"). מחיר שגוי שנופל בין 55% ל-100% עובר, ולכן הבדיקה הידנית נדרשת.
5. אם `ok` הוא `false` ו-`error` אומר `HTTP 4xx` או `unexpected response`, זה סימן שהמתאם אינו מתאים לשירות החי (ראו התנאי 5 למעלה). מסירים את הסוד (`npx wrangler secret delete <NAME>`) ומדווחים לי, והמקור חוזר להיות לא מוגדר ולא עולה כלום.
6. רק אז עוברים למקור הבא.

**מה קורה כשמכסה נגמרת:** המקור מופיע ב-`meta.sources` עם `error` "free quota used up", הוא לא נקרא עוד, והחיפוש ממשיך עם Travelpayouts ועם המקורות האחרים. המונה של מקור חודשי מתחיל מחדש בחודש UTC הבא. מונה של מכסה חד-פעמית **לא** מתאפס לעולם: אחרי שנגמר, המקור נשאר כבוי לצמיתות.

**מנת היום נגמרה:** המקור מופיע ב-`meta.sources` עם `error` "today's share of the free quota used up", לא נקרא עד חצות UTC, והמונה האמיתי שלו לא זז. זה לא סימן לתקלה. לראות את המנות של היום: `npx wrangler d1 execute eee-db --remote --command "SELECT key, count FROM rate_limits WHERE key LIKE 'quota:%'"` (קריאה בלבד).

**מפתח שגוי או שנשלל:** כל בקשה שנשלחה נספרת, גם אם נדחתה עם HTTP 401. מנת היום מגבילה את הנזק לכמה יחידות ביום, אבל מונה חד-פעמי לא חוזר לבד. אחרי שמתקנים מפתח (או מסירים אותו) אפשר להחזיר את המונה ידנית, **ורק** כשלוח הבקרה של הספק מראה שהמכסה שלו באמת עוד פנויה במספר הזה:

```bash
npx wrangler d1 execute eee-db --remote --command "UPDATE source_quota SET used = <הצריכה האמיתית לפי לוח הבקרה של הספק> WHERE source = 'ignav' AND period = 'lifetime'"
```

הערך לא יורד אף פעם מתחת לצריכה האמיתית: זו הפעולה היחידה בכל התהליך שיכולה להוביל לחריגה מהמכסה, ולכן היא ידנית ובבדיקה מול הספק. אין לשנות מונה של תקופה חודשית באמצע החודש.

**חיפוש איטי:** כל שלב המקורות החיים מוגבל ל-6 שניות. מה שחזר עד אז משולב בדירוג, בקשה שעדיין רצה מדווחת כ"timeout" (היחידה שלה כבר נספרה), ובקשה שלא התחילה לא תתחיל. סריקת Travelpayouts נשמרת (מטמון, יומן חיפושים, בריאות מקור) **לפני** שמתחיל השלב הזה, כך שלקוח שמבטל באמצע לא מפסיד אותה.

**מה המונה לא רואה:** בקשות שנעשו עם אותו מפתח מחוץ ל-Worker (לוח ניסויים באתר הספק, סקריפט אישי). לכן התקרות נמוכות מהמכסה, ולכן לא משתמשים באותו מפתח בשום מקום אחר.

### בדיקת "זוג או בנפרד?" (`POST /api/party-check`, `worker/src/partycheck.ts`)

**החלק החינמי לא צריך כלום:** בחיפוש של 2 מבוגרים ומעלה יש בכל כרטיס תיבה "זוג או בנפרד?" (מ-3 מבוגרים: "ביחד או בנפרד?") עם שני קישורים לאתר ההזמנה, לנוסע אחד ולכל הקבוצה, כדי שהמשתמש ישווה בעצמו. הקישורים הם הקישור של הכרטיס עצמו עם מספר נוסעים אחר, בלי מפתח ובלי שום קריאה לשירות. (הקוד של מספר הנוסעים בקישור של כמה מבוגרים הוא הסקה מהקישורים של נוסע אחד, ולא נבדק מול האתר החי.)

**הבדיקה האוטומטית (הכפתור "בדקו בשבילי אוטומטית") משתמשת ב-2 חיפושים מהמכסה החינמית של המקור בכל לחיצה:** אחד לנוסע אחד ואחד לכל הקבוצה. היא רצה **רק כשמשתמש לוחץ**, אף פעם לא אוטומטית ואף פעם לא ברקע, ורק על כרטיס מחיפוש אמיתי מהיממה האחרונה: החיפוש חותם על המסלול, התאריכים ומספר המבוגרים של כל כרטיס הלוך־חזור (HMAC עם `RATE_LIMIT_SALT`, ובלעדיו סוד שנגזר מהטוקן של Travelpayouts), ובקשה בלי חתימה תקפה נדחית (400) לפני כל דבר אחר: בלי שער חליפין, בלי מונה ובלי קריאה לספק. (החלפת `RATE_LIMIT_SALT` רק מבטלת את החתימות של תוצאות שכבר מוצגות: המשתמש יחפש שוב.) שתי היחידות נלקחות מהמונה וממנת היום **לפני** הקריאה הראשונה, הכול או כלום: אם נשארה פחות משתיים, לא נשלחת אף קריאה. אין ניסיון חוזר. כשל בקריאה הראשונה עוצר את השנייה, וכך גם תשובה ראשונה בלי מחיר שאפשר להשוות. בנוסף: 3 בדיקות ל-10 דקות לכל משתמש, ולכל מקור לכל היותר חצי ממנת היום שלו ולא יותר מ-5 בדיקות ביום (מונה `party:<מקור>` בטבלה `rate_limits`). הכפתור מוצג רק כשלמקור יש מקום לבדיקה: 2 יחידות מתחת לתקרה ובמנת היום, ומקום במונה הבדיקות של היום.

**איזה מקור מותר:** רק מקור שהתיעוד שלו מאפשר לדעת אם מחיר של כמה מבוגרים הוא לכולם או לנוסע אחד, ושמנת היום שלו מספיקה לבדיקה. לפי התיעוד (נקרא ב-30.9.2026, הקישורים בראש כל קובץ ב-`worker/src/sources/`): SerpApi, SearchApi ו-Ignav מקבלים מספר מבוגרים אבל לא אומרים איך המחיר מחושב; Duffel כן מתעד `total_amount` כסכום לכל הנוסעים, אבל בדיקת הפרדה נשארת אחרי המקורות הקיימים בסדר הבחירה, ולכן לא משתמשים בהם לבדיקה. אצל Wego התיעוד **לא** אומר במפורש לאילו נוסעים `totalAmount` ("total amount") מתייחס. לצד `amount` ("average amount for all passengers") ו-`amountPerAdult` ("amount per adult passenger") אנחנו **מסיקים** שזה הסכום לכל הנוסעים. זו הסקה ולא עובדה מתועדת, ולכן הקוד בודק אותה בכל מחיר: מחיר של כמה מבוגרים נקרא רק אם הוא מוסר גם מחיר לנוסע (`amount`, `originalAmount` או `amountPerAdult`), וכל אחד מהם כפול מספר המבוגרים שווה לסכום. מחיר בלי מחיר לנוסע לא נקרא בכלל. מנת היום של Wego היא בקשה אחת (תקרה 30), ובדיקה של שתי בקשות לא נכנסת בה. **לכן היום הכפתור לא מוצג גם אם כל המפתחות מוגדרים, ו-`POST /api/party-check` עונה 404.** זה מכוון, לא תקלה. החלק החינמי עובד כרגיל.

**שימו לב:** העלאת התקרה של Wego ל-91 ומעלה (`WEGO_QUOTA` ב-`worker/src/sources/wego.ts`, עם `allowance` של 102 לפחות) **תפעיל** את הבדיקה האוטומטית על Wego, על סמך ההסקה שלמעלה והבדיקה שלה בכל מחיר.

לראות כמה בדיקות נעשו היום (קריאה בלבד): `npx wrangler d1 execute eee-db --remote --command "SELECT key, count FROM rate_limits WHERE key LIKE 'party:%' AND window_start = CAST(strftime('%s', 'now', 'start of day') AS INTEGER)"`

## 6ב. התראות מחיר בטלגרם (אופציונלי, חינם)

**מה זה נותן:** משתמש שומר חיפוש (`POST /api/watches`), מקבל קישור לבוט בטלגרם, ולוחץ Start. מאותו רגע ה-Worker בודק את החיפוש **בערך פעם ביום** ושולח לו הודעה בעברית כשמופיע מחיר טוב: מתחת למחיר יעד שבחר, ירידה של X% מהמחיר הראשון שנמצא (ברירת מחדל 10%), או מחיר חריג לפי גלאי הדילים (`deals.ts`). בכל הודעה: המחיר הכולל לכל הנוסעים, התאריכים, ציון מפורש שזה מחיר שמור שעשוי להשתנות, קישור להזמנה, והפקודות `/stop_<מספר>` (הפסקת ההתראה הזו) ו-`/stop` (הפסקה ומחיקה של כולן). לכל היותר הודעה אחת ביום לכל התראה, ואותה רמת מחיר לא נשלחת שוב.

**למה טלגרם:** ה-Bot API של טלגרם חינמי לגמרי, בלי מסלול ובלי כרטיס, ואין מחיר להודעה.
- **WhatsApp לא מומש, בכוונה:** WhatsApp Business Platform של Meta גובה תשלום לכל שיחה או הודעה יזומה (הודעות "תבנית" כמו התראה), ודורש חשבון עסקי עם אמצעי תשלום. זה נוגד את הכלל "שום דבר לא עולה כסף".
- **מייל: אפשרות לעתיד, לא מומש.** אפשר להוסיף ערוץ מייל במסלול חינמי (Cloudflare Email Workers / Email Routing, או ספק עם מסלול חינמי כמו Resend) רק עם **תקרה קשיחה יומית נמוכה מהמכסה החינמית**, מונה ב-D1 שעולה לפני כל שליחה, כשל סגור ובלי כרטיס בחשבון, כמו המקורות בסעיף 6א. מייל הוא גם מידע אישי נוסף, ולכן טלגרם עדיף כברירת מחדל.

**בלי ההגדרות הערוץ פשוט כבוי (כשל סגור):** כל עוד לא הוגדרו שלושתם, `POST /api/watches` עונה 503 `alerts_unavailable`, ה-webhook עונה 404, והמשימה המתוזמנת לא בודקת ולא שולחת כלום (רק מנקה התראות שפג תוקפן).

**מה נשמר (פרטיות):** אין חשבונות ואין סיסמאות. ההתראה שייכת למי שמחזיק ב-token שלה (256 ביט אקראי); ב-D1 נשמר רק גיבוב SHA-256 שלו. איש הקשר היחיד הוא מזהה הצ'אט בטלגרם, והוא נמחק כשההתראה נעצרת (`/stop`, `DELETE`) או פגה. בנוסף נשמר גיבוב מולח של כתובת הלקוח (כמו במגבלת הקצב), רק כדי לאכוף את התקרה ללקוח.

**תקרות (בקוד, `worker/src/watches.ts`):** עד 3 התראות פעילות ללקוח, 5 לצ'אט, 300 בסך הכול (כך שהריצות השעתיות באמת מספיקות לבדוק כל התראה פעם ביום); יצירה: 6 בקשות לשעה ללקוח; קריאה/מחיקה: 60 ל-10 דקות; הבוט עונה לצ'אט עד 20 פעמים ב-10 דקות. התראה פגה אחרי 60 יום או ביום שאחרי תאריך היציאה האחרון האפשרי, המוקדם מביניהם; התראה שלא חוברה לטלגרם תוך 48 שעות נמחקת.

**איך הבדיקה היומית נשארת בחינם:** טריגר cron שעתי (`29 * * * *`, השלישי מתוך 5 שמותרים במסלול החינמי) לוקח בכל ריצה עד 20 התראות שלא נבדקו 20 שעות, כך שכל התראה נבדקת בערך פעם ביום. המחיר נלקח **קודם מהיסטוריית המחירים ב-D1** (טבלת `prices`, שכל חיפוש ו-snapshot ממלאים). SQL מחזיר רק את המחיר העדכני ביותר של כל זוג תאריכים (מחיר ישן וזול שסריקה חדשה החליפה לא נחשב), מחיר חי של מקור אופציונלי נחשב רק עד 6 שעות, ומצב הבדיקה נכתב תוך כדי הריצה (כל 4 פעולות), כך שריצה שנקטעה לא מאבדת את מה שסיימה. רק להתראה בלי מחיר עדכני (עד 26 שעות) נעשית סריקה חיה קטנה: זוג השדות הראשי בלבד, הלוך-חזור בלבד, עד 6 בקשות ל-Travelpayouts, עד 2 סריקות לריצה, וכל אחת לוקחת יחידה מתקציב הסריקות הגלובלי של החיפוש. כל שאילתת D1 וכל בקשה יוצאת של ריצה נספרות **מראש** מול תקציב של 45 (מתחת ל-50 של המסלול החינמי, גם אם D1 נספר בו); מה שלא נכנס נדחה לריצה הבאה.

**שלבים (אתה מבצע; אני לא יוצר חשבונות ולא נוגע בסודות):**

1. מריצים את מיגרציה 0006 (סעיף 4).
2. בטלגרם פותחים שיחה עם **@BotFather** (החשבון הרשמי, עם סימן V כחול), שולחים `/newbot`, בוחרים שם תצוגה (למשל "התראות טיסות") ושם משתמש שנגמר ב-`bot` (למשל `EeeFlightsBot`). BotFather מחזיר **טוקן** בצורה `123456789:AA…`. **זה סוד:** לא בצ'אט, לא בקוד, לא ב-Issue.
3. (מומלץ) אצל BotFather: `/setcommands`, בוחרים את הבוט ומדביקים:
   ```
   list - ההתראות הפעילות שלי
   stop - הפסקה ומחיקה של כל ההתראות
   help - עזרה
   ```
4. יוצרים סוד webhook אקראי (16–256 תווים מתוך A-Z a-z 0-9 _ -), למשל: `openssl rand -hex 32`.
5. מגדירים ב-Worker (סעיף 6), שני סודות ומשתנה אחד:
   ```bash
   cd eee/worker
   npx wrangler secret put TELEGRAM_BOT_TOKEN        # הטוקן מ-BotFather
   npx wrangler secret put TELEGRAM_WEBHOOK_SECRET   # המחרוזת מצעד 4
   ```
   `TELEGRAM_BOT_USERNAME` (שם המשתמש של הבוט, בלי @) אינו סוד. כדי שלא יימחק בהעלאה הבאה (ראו סעיף 6), מוסיפים אותו ל-`wrangler.toml` תחת `[vars]`, למשל `TELEGRAM_BOT_USERNAME = "EeeFlightsBot"`, או אומרים לי ואוסיף.
6. רושמים את ה-webhook אצל טלגרם (פעם אחת; מחליפים את `<TOKEN>`, `<URL>` ו-`<SECRET>`. הפקודה נשלחת ישירות לטלגרם, לא לשום שירות אחר):
   ```bash
   curl -sS "https://api.telegram.org/bot<TOKEN>/setWebhook" \
     -d "url=https://<URL>/api/telegram/webhook" \
     -d "secret_token=<SECRET>" \
     -d 'allowed_updates=["message"]'
   # צפוי: {"ok":true,"result":true,"description":"Webhook was set"}
   ```
   טלגרם שולח מאז בכל עדכון את הכותרת `X-Telegram-Bot-Api-Secret-Token`; בקשה בלי הסוד הנכון נדחית ב-401.
7. בדיקה: `curl -sS "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"` מראה את הכתובת ו-`pending_update_count` נמוך. אחר כך:
   ```bash
   curl -sS -X POST URL/api/watches -H 'Content-Type: application/json' \
     -d '{"origin":"TLV","destination":"BCN","windowStart":"<תאריך עתידי>","windowEnd":"<+14 יום>","stayMin":4,"stayMax":7,"targetPriceIls":1500}'
   # צפוי: 201 עם "token", "telegramLink" ו-"watch":{"status":"pending",...}
   ```
   פותחים את `telegramLink`, לוחצים Start, ומקבלים "✅ ההתראה הופעלה!". `GET URL/api/watches/<token>` מראה עכשיו `"status":"active"`. שולחים לבוט `/stop` ומוודאים שההתראה נמחקה (`GET` מחזיר 404).

**כיבוי:** `npx wrangler secret delete TELEGRAM_BOT_TOKEN` מכבה את הערוץ מיד (כשל סגור). למחיקת ה-webhook: `curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook"`. טוקן שנחשף מבטלים אצל BotFather (`/revoke`) ומגדירים מחדש.

**לא נבדק מול השירות החי:** הקוד נבדק רק מול תחליפים מקומיים (אין בוט אמיתי). הפורמט של Bot API (`sendMessage`, תשובה דרך גוף ה-webhook, `link_preview_options`, הכותרת הסודית) נכתב מהתיעוד הרשמי. ההפעלה הראשונה היא הבדיקה.

## 6ג. נעילת האתר לשימוש אישי (סוד אחד, חינם)

**מה זה נותן:** כשהסוד `ACCESS_KEY` מוגדר, ה-API עונה רק למי ששולח את המפתח. **כל הנתונים נעולים:** חיפוש, השלמה אוטומטית, לוח מחירים, "לא יודע לאן?", מבצעים, התראות, וגם כל נתיב שיתווסף בעתיד (למשל מענפים אחרים). השער (`worker/src/access.ts`) הוא "הכול נעול חוץ מ־", לא רשימת נתיבים לנעילה, ולכן אי אפשר לשכוח לנעול נתיב חדש. **הדף עצמו (Pages) נשאר נגיש, אבל בלי המפתח הוא מציג רק מסך נעילה.** בקשה בלי מפתח נדחית לפני כל מגבלת קצב, קריאה ל-D1 או מטמון, כך שהיא לא צורכת כלום מהמכסות.

**מה נשאר פתוח, בכוונה:**
- `GET /api/health` — לניטור ולבדיקת העשן. הוא מראה רק אם הנעילה פעילה (`"locked":true` ו-`"lockStatus":"on" | "off" | "misconfigured"`), אף פעם לא את המפתח או משהו עליו. זה הנתיב היחיד שקורא מ-D1 בלי מפתח: שתי קריאות זעירות של בדיקת חיות, כמו לפני הנעילה (מכסת הבקשות החינמית של ה-Worker נגמרת הרבה לפני מכסת הקריאות של D1).
- `POST /api/telegram/webhook` — השרתים של טלגרם לא יכולים להחזיק את המפתח; לנתיב הזה יש סוד משלו (סעיף 6ב).
- בקשות CORS מקדימות (`OPTIONS`) — דפדפן אף פעם לא שולח בהן מפתח, והן לא מחזירות נתונים. כשהנעילה פעילה כולן מקבלות אותה תשובה בדיוק, בכל נתיב, כך שגם הן לא מגלות אילו נתיבים קיימים.

**למה לא Cloudflare Access / Zero Trust:** הם עלולים לבקש אמצעי תשלום, והכלל כאן הוא ששום דבר לא עולה כסף. הנעילה הזו היא קוד בלבד, בחינם.

**שלבים (אתה מבצע; המפתח לא עובר בצ'אט). הסדר חשוב: קודם הקוד, בסוף הסוד.**

1. מעלים את הקוד של הנעילה: ה-Worker (סעיף 5) **וגם** ממשק Pages (`web/README.md`), בכל סדר ביניהם. בלי הסוד שום דבר עוד לא ננעל. בודקים ששניהם באוויר:
   ```bash
   curl -s URL/api/health        # ..."locked":false,"lockStatus":"off"  (בלי השדות האלה: גרסת ה-Worker הישנה עוד באוויר)
   ```
   ואת האתר פותחים פעם אחת, כדי לוודא שנטענה הגרסה החדשה.
2. יוצרים מפתח אקראי במחשב שלך (יוצאים 32 תווים):
   ```bash
   node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
   ```
   שומרים אותו במנהל הסיסמאות. **לא מדביקים אותו בצ'אט, במייל, בקוד או ב-Issue.**
3. **רק עכשיו** מגדירים אותו כסוד ב-Worker. הערך נשאל אינטראקטיבית: מדביקים את המפתח **שם**, ולא בשורת הפקודה:
   ```bash
   cd worker
   npx wrangler secret put ACCESS_KEY
   ```
   או בדשבורד: Workers & Pages ← `eee-api` ← Settings ← Variables and Secrets ← Add ← סוג **Secret** ← בשדה Variable name כותבים `ACCESS_KEY` ← בשדה Value מדביקים את המפתח ← **Deploy**. בשתי הדרכים נוצרת גרסה חדשה של ה-Worker עם הסוד ועולה מיד, ובלבד שהגרסה שבאוויר היא כבר זו עם הנעילה (שלב 1): אין צורך בהעלאה נוספת.
4. בודקים (מחליפים `URL` בכתובת ה-Worker):
   ```bash
   curl -s URL/api/health        # ..."locked":true,"lockStatus":"on"
   curl -i URL/api/deals         # HTTP 401  {"error":{"code":"unauthorized","message":"Access key required"}}
   ```
5. פותחים את האתר ומדביקים את המפתח במסך הנעילה, **פעם אחת בכל מכשיר ובכל דפדפן**. הוא נשמר רק בדפדפן הזה (localStorage, בשם `eee.accessKey`; בגלישה פרטית הוא נמחק לכל המאוחר כשסוגרים את החלון הפרטי), ונשלח רק בכותרת `Authorization` של הקריאות ל-API: לא בכתובת, לא ביומנים ולא במטמון של ה-service worker.
6. בדיקת העשן אחרי העלאה, עם המפתח, בלי שיישמר בהיסטוריית המסוף ובלי שיישאר במשתני הסביבה אחר כך (הסוגריים מריצים הכול בתת-מעטפת שנסגרת בסוף):
   ```bash
   ( read -rs EEE_ACCESS_KEY && export EEE_ACCESS_KEY && bash scripts/smoke.sh )
   ```
   **המסוף לא מציג כלום אחרי הפקודה, וזה בכוונה:** מדביקים את המפתח (הוא לא יופיע על המסך) ולוחצים Enter. בלי המפתח הסקריפט מדפיס "האתר נעול: הריצו EEE_ACCESS_KEY=... bash scripts/smoke.sh", ומיד אחריה את הדרך הבטוחה שלמעלה, ונכשל. שורת "מצב הנעילה" מראה `on` / `off` / `misconfigured`. הסקריפט לא מדפיס את המפתח.

**למה קודם הקוד ובסוף הסוד:** אם הסוד פעיל ב-Worker לפני שהממשק החדש עלה, הממשק הישן (שאין בו מסך נעילה) מקבל 401 בכל קריאה, מציג "משהו השתבש אצלנו", ואין בו שום מקום להזין את המפתח. זה קל לפספס: ה-Worker יכול לעלות לבד עם כל מיזוג ל-`main` (Workers Builds, סעיף 5), אבל את Pages מעלים ידנית. ואם הסוד כבר הוגדר קודם (למשל על הגרסה הישנה, שמתעלמת ממנו), הנעילה נדלקת ברגע שגרסת ה-Worker עם הנעילה עולה: אז מעלים קודם את Pages. בכיוון השני אין בעיה: הממשק החדש עובד גם מול Worker ישן (בלי `/api/auth/check` הוא פשוט לא נועל), והקוד החדש בלי הסוד מתנהג בדיוק כמו הישן.

**כללי המפתח:** 20–256 תווים גלויים באנגלית (אותיות, ספרות וסימנים), בלי רווחים. המחולל בשלב 2 נותן 32. מפתח קצר מ-20 תווים (או ארוך מ-256, או עם רווח או עברית) הוא **הגדרה שגויה, והאתר נסגר לגמרי (כשל סגור)**: כל נתיב מוגן עונה 503 `access_misconfigured` ולא מחזיר נתונים, ו-`/api/health` מראה `"lockStatus":"misconfigured"`. במסך הנעילה כתוב "האתר לא מוגדר נכון (המפתח קצר מדי)" כשהסוד קצר מדי, ו"האתר לא מוגדר נכון (המפתח לא תקין)" כשהוא ארוך מדי או עם רווח או עברית; במקום שדה המפתח (שלא יכול לעזור) יש כפתור "נסו שוב". מתקנים בהגדרה מחדש של הסוד (שלב 3), ואז לוחצים "נסו שוב".

**ניחושים:** אחרי 20 ניסיונות עם מפתח שגוי בתוך 10 דקות מאותה כתובת, כל בקשה מוגנת מהכתובת הזו מקבלת 429 עם `Retry-After` עד סוף החלון, גם עם המפתח הנכון (אחרת אפשר היה לזהות ניחוש מוצלח). המונה נשמר רק בזיכרון של ה-Worker, לא ב-D1, ולכל מופע של ה-Worker מונה משלו. במסך הנעילה כתוב "יותר מדי ניסיונות, נסו שוב בעוד N דקות"; כשהמפתח כבר שמור בדפדפן לא צריך להקליד אותו שוב: הכפתור "נסו שוב" נפתח כשהזמן עובר. מפתח שקצר מ-20 תווים (הדבקה חלקית) נדחה עוד בדפדפן ולא נספר כניסיון. כל מי שיוצא לאינטרנט מאותה כתובת (למשל אותה רשת ביתית) נספר יחד, כולל תוסף הדפדפן אם נשאר בו מפתח ישן. עם מפתח אקראי של 32 תווים ניחוש לא מעשי ממילא.

**יציאה ממכשיר:** בתחתית כל עמוד מופיע "יציאה (מחיקת המפתח מהמכשיר)" כשיש מפתח שמור.

**החלפת מפתח** (אם נחשף, או סתם): מריצים שוב `npx wrangler secret put ACCESS_KEY` עם ערך חדש. כל מכשיר יבקש את המפתח החדש: הישן נמחק ממנו אוטומטית בבקשה הראשונה שנדחית, ובמסך הנעילה כתוב "המפתח שנשמר במכשיר הזה כבר לא תקף. הזינו את המפתח העדכני." **מעדכנים מיד גם את התוסף:** כל קריאה שלו עם המפתח הישן נספרת כניסיון שגוי מהכתובת שלך, ו-20 כאלה חוסמים אותה ל-10 דקות.

**ביטול הנעילה:** `npx wrangler secret delete ACCESS_KEY`. האתר חוזר מיד להיות פתוח לכולם, גם בדפדפנים שעוד שומרים מפתח.

**תוסף הדפדפן (בענף נפרד):** גם הוא קורא ל-API, ולכן כשהנעילה פעילה הוא יצטרך את אותו מפתח בהגדרות שלו (נשלח ככותרת `Authorization: Bearer <המפתח>`), ולהפסיק לשלוח אחרי 401 (ראו "החלפת מפתח").

**עלות:** אפס. אין שירות נוסף ואין קריאות או כתיבות ל-D1 בגלל הנעילה; בקשה שנדחית היא רק הפעלה אחת של ה-Worker (מתוך 100,000 החינמיות ביום). כשמפתח שמור, הדפדפן שולח לפני קריאות ה-API בקשת CORS מקדימה (`OPTIONS`) ושומר אותה במטמון שלו (בכרום עד שעתיים לכל כתובת). בשימוש אישי זה רחוק מאוד מהמכסה.

## 7. שלב ד' — אימות (מחליפים `URL` בכתובת שלך)

כל הפלטים כאן נבדקו מקומית; ב-Cloudflare הם אמורים להיות זהים. **אם הנעילה פעילה (סעיף 6ג)**, כל קריאה חוץ מ-`/api/health` צריכה גם `-H "Authorization: Bearer $KEY"`; בלעדיו התשובה היא 401. את המפתח מכניסים עם `read -rs KEY`, כדי שלא יישמר בהיסטוריה: המסוף לא מציג כלום, מדביקים ולוחצים Enter. בסוף הבדיקות מריצים `unset KEY`.

```bash
URL=https://eee-api.<שלך>.workers.dev

# 1) בריאות (כולל בדיקת D1)
curl -i $URL/api/health
#   HTTP 200, Cache-Control: no-store, X-Content-Type-Options: nosniff
#   {"status":"ok","db":"ok","build":{"sha":"<קומיט>","time":"<זמן ההעלאה>"},"migration":"0006_m11_price_alerts.sql","migrationsPending":false,"locked":false,"lockStatus":"off"}
#   (עם הנעילה של סעיף 6ג: "locked":true,"lockStatus":"on". הבריאות עונה גם בלי המפתח, ואף פעם לא מציגה אותו)

# 2) השלמה אוטומטית בעברית
curl -G $URL/api/airports --data-urlencode "q=ברצלונה"
#   {"results":[{"code":"BCN","nameHe":"ברצלונה","nameEn":"Barcelona","countryCode":"ES","kind":"city","airports":["BCN"]}]}

# 3) חיפוש בלי טוקן של Travelpayouts (מצב צפוי לפני שסעיף 6 הושלם)
curl -i -X POST $URL/api/search -H 'content-type: application/json' \
  -d '{"origin":"תל אביב","destination":"ברצלונה","windowStart":"2026-11-10","windowEnd":"2026-11-25","stayMin":5,"stayMax":7}'
#   HTTP 503  {"error":{"code":"source_unavailable","message":"No fare source is available right now"}}
#   אחרי שהוגדר TRAVELPAYOUTS_TOKEN: HTTP 200 עם "cards" ו-"meta" (מבנה מלא ב-docs/WEB_APP_SPEC.md §7.2)

# 4) שגיאת קלט
curl -i -X POST $URL/api/search -H 'content-type: application/json' \
  -d '{"origin":"TLV","destination":"BCN","windowStart":"2020-01-01","windowEnd":"2020-01-05","stayMin":5,"stayMax":7}'
#   HTTP 400  {"error":{"code":"invalid_request",...,"fields":{"windowStart":"must not be in the past",...}}}

# 5) שיטה שגויה / נתיב לא קיים / גוף גדול מדי
curl -i $URL/api/search            # 405 + Allow: POST, OPTIONS
curl -i $URL/nope                  # 404
#   גוף של יותר מ-8192 בתים ל-POST /api/search -> 413 {"error":{"code":"payload_too_large",...}}

# 6) מגבלת קצב: 30 חיפושים ל-10 דקות ללקוח. הבקשה ה-31 נדחית
for i in $(seq 1 31); do curl -s -o /dev/null -w "%{http_code} " -X POST $URL/api/search -H 'content-type: application/json' -d '{}'; done
#   צפוי: 400 עד שהמכסה נגמרת, ואז 429 עם Retry-After ו-{"error":{"code":"rate_limited",...}}
```

בדיקות נוספות בדשבורד:
- **Cron:** Workers & Pages ← `eee-api` ← Settings ← Trigger Events: רואים `17 3 * * *`.
- **יומן חי:** `npx wrangler tail eee-api` (או לשונית Logs בדשבורד).
- **אין CORS עד שמגדירים `ALLOWED_ORIGIN`:** תשובת OPTIONS היא 204 בלי כותרות `Access-Control-*`. זה מכוון.

**כיסוי הנתונים (השער D1 באפיון):** אחרי שהטוקן מוגדר, מריצים את Phase 0 לכמה מסלולים מתל אביב ומאילת (GitHub ← Actions ← "Phase 0 - price proof" ← Run workflow) ובודקים ש-Travelpayouts מחזיר מחירים. זו השאלה הפתוחה החוסמת של הפרויקט.

## 9. תפעול

- **ניטור:** Workers & Pages ← `eee-api` ← Metrics (בקשות, שגיאות, זמן CPU); D1 ← `eee-db` ← Metrics.
- **גיבוי גרסה קודמת (Rollback):** `eee-api` ← **Deployments** ← שלוש נקודות ליד גרסה קודמת ← **Rollback** (עד 100 גרסאות אחרונות). או `npx wrangler rollback`. **הנתונים ב-D1 לא חוזרים אחורה**, וההעלאה של קוד שתלוי במבנה מסד חדש דורשת זהירות.
- **שחזור מסד:** ל-D1 יש שחזור לנקודת זמן (Time Travel). בדוק בדשבורד תחת `eee-db` מה תקופת השמירה במסלול שלך לפני שאתה מסתמך עליו.
- **אל תמחק את `eee-db`:** בו נשמר היסטוריית המחירים והמטמון.
